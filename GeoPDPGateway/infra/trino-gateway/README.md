# Trino Gateway

Deploys the official `trino/trino-gateway` Helm chart into the `default`
namespace and uses the PostgreSQL credentials already provisioned for the base
Hive Metastore. Gateway metadata is kept in the existing `trinodb` database;
query-history persistence is disabled. The Gateway stores its configuration in
a Kubernetes Secret generated by the chart.

## Install / upgrade

From the repository root, the following command reads the database credentials
from the existing Kubernetes Secret without printing them and supplies them to
Helm at deployment time:

```sh
DB_USER="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_USER}' | base64 -d)"
DB_PASSWORD="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_PASSWORD}' | base64 -d)"
DB_HOST="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_HOST}' | base64 -d)"
DB_PORT="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_PORT}' | base64 -d)"
DB_NAME="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_NAME}' | base64 -d)"

helm upgrade --install trino-gateway trino/trino-gateway \
  --version 1.21.0 \
  --namespace default \
  --values infra/trino-gateway/values.yaml \
  --set-string "config.dataStore.jdbcUrl=jdbc:postgresql://${DB_HOST}:${DB_PORT}/${DB_NAME}" \
  --set-string "config.dataStore.user=${DB_USER}" \
  --set-string "config.dataStore.password=${DB_PASSWORD}" \
  --wait --timeout 10m
unset DB_USER DB_PASSWORD DB_HOST DB_PORT DB_NAME
```

The configured `host.docker.internal` database host matches the current local
Hive Metastore setup. Ensure the PostgreSQL role/database allows the Gateway's
Flyway migrations; a dedicated Gateway database and role are preferable outside
this local POC. Helm release values also contain the datastore password, so use
appropriate access controls for Kubernetes Secrets and Helm release records.

## Connect the Trino clusters

Gateway's default route group is `adhoc`. Once the Gateway is ready, forward its
service and register the two in-cluster coordinator Services through the Gateway
management API:

```sh
kubectl port-forward -n default svc/trino-gateway 9093:8080
```

In another terminal:

```sh
curl -X POST http://localhost:9093/gateway/backend/modify/add \
  -H 'Content-Type: application/json' \
  -d '{"name":"base","proxyTo":"http://trino.default.svc.cluster.local:8080","active":true,"routingGroup":"adhoc"}'

curl -X POST http://localhost:9093/gateway/backend/modify/add \
  -H 'Content-Type: application/json' \
  -d '{"name":"georestricted","proxyTo":"http://georestricted-trino.georestricted.svc.cluster.local:8080","active":true,"routingGroup":"georestricted"}'
```

## Local policy/routing POC

See the [trinoGateway run guide](../../trinoGateway/README.md) for dependency
installation, the Uvicorn startup command, and sample API calls. The independent
metadata-driven PDP policy is in `pdp/`: it allows `trades_raw` only from `US`
and routes it to `georestricted`, while `tpch` is allowed from any configured
location and routed to `adhoc`. Denials use the external selector's `errors`
response field.

The current Helm values enable request analysis but leave
`routingRules.rulesEngineEnabled` false. They also contain a placeholder
in-cluster URL. This POC currently runs locally and is not packaged/deployed as
a Kubernetes service, so the Gateway pod cannot reach the adapter at that
placeholder address. Before integration, deploy or otherwise expose the API at
a URL reachable by the Gateway, enable the external rules engine, and verify
deny/error propagation against the exact Gateway version. Do not rely on
client-provided routing headers.

See the repository-root [POC limitations](../../POC_LIMITATIONS.md) for the
scope, security caveats, and follow-up requirements. This routing demo is not
an authorization boundary.

## Important security limitation

This is routing, not an authorization boundary. In particular, Gateway's
external-selector fallback behavior and client-supplied routing headers must not
be relied on to enforce data sovereignty. Before using real restricted data,
authenticate the location claim, fail closed when the policy service is
unavailable, and enforce the same access decision in Trino access control (or
another trusted authorization layer).
