# Trino Gateway

Deploys the official `trino/trino-gateway` Helm chart into the `default`
namespace and uses the PostgreSQL credentials already provisioned for the base
Hive Metastore. Gateway metadata is kept in the existing `trinodb` database;
query-history persistence is disabled. The Gateway stores its configuration in
a Kubernetes Secret generated by the chart.

For the complete Entra → Gateway selector → PDP → Trino OAuth → query-result
walkthrough, including invoking a SQL query through the Gateway protocol API,
follow the [end-to-end runbook](../../trinoGateway/README.md).
The query client example is `python scripts/query_gateway.py 'SELECT * FROM tpch.sf1.customer LIMIT 5'`;
the SQL request goes to Gateway, while `/gateway-rules` remains an internal
Gateway-to-policy callback and must not be called as a SQL endpoint.

## Install / upgrade

From the repository root, the following command reads the database credentials
from the existing Kubernetes Secret without printing them and supplies them to
Helm at deployment time:

```sh
DB_USER="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_USER}' | base64 -d)"
DB_PASSWORD="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_PASSWORD}' | base64 -d)"
DB_HOST="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_HOST}' | base64 -d)"
DB_PORT="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_PORT}' | base64 -d)"
DB_NAME="$(kubectl get secret hive-metastore-db-secret -n default -o jsonpath='{.data.DB_NAME}' | base64 -d)"

helm upgrade --install trino-gateway trino/trino-gateway \
  --version 1.21.0 \
  --namespace default \
  --values infra/trino-gateway/values.yaml \
  --set-string "config.dataStore.jdbcUrl=jdbc:postgresql://${DB_HOST}:${DB_PORT}/${DB_NAME}" \
  --set-string "config.dataStore.user=${DB_USER}" \
  --set-string "config.dataStore.password=${DB_PASSWORD}" \
  --wait --timeout 10m
unset DB_USER DB_PASSWORD DB_HOST DB_PORT DB_NAME
```

The configured `host.docker.internal` database host matches the current local
Hive Metastore setup. Ensure the PostgreSQL role/database allows the Gateway's
Flyway migrations; a dedicated Gateway database and role are preferable outside
this local POC. Helm release values also contain the datastore password, so use
appropriate access controls for Kubernetes Secrets and Helm release records.

## Connect the Trino clusters

Gateway's default route group is `adhoc`. Once the Gateway is ready, forward its
service and register the two in-cluster coordinator Services through the Gateway
management API:

```sh
kubectl port-forward -n default svc/trino-gateway 9093:8080
```

In another terminal:

```sh
curl -X POST http://localhost:9093/gateway/backend/modify/add \
  -H 'Content-Type: application/json' \
  -d '{"name":"base","proxyTo":"http://trino.default.svc.cluster.local:8080","active":true,"routingGroup":"adhoc"}'

curl -X POST http://localhost:9093/gateway/backend/modify/add \
  -H 'Content-Type: application/json' \
  -d '{"name":"georestricted","proxyTo":"http://georestricted-trino.georestricted.svc.cluster.local:8080","active":true,"routingGroup":"georestricted"}'
```

These HTTP backend examples describe the current local cluster services; they
are not an authenticated endpoint on their own. Complete the end-to-end
runbook's Trino OAuth, trusted HTTPS/forwarded-header, and coordinator
validation steps before enabling the Gateway callback or accepting credentials.

## Deploy the identity-aware selector

Build `Dockerfile.routing-api` as `geo-pdp-routing-api:dev`, make that image
available to the local Kubernetes cluster, replace the Entra tenant and API
audience placeholders in [routing-api.yaml](routing-api.yaml), then apply that
manifest. It creates the `routing-api` Service referenced by the Gateway values.
The selector needs the Entra v2 issuer, matching access-token audience, tenant
JWKS endpoint, and a configured `geo_location` claim. This claim is controlled
test data and is not evidence of live physical location.

Both safeguards are off by default: the selector ConfigMap sets
`TRINO_OAUTH_ENFORCED=false`, and Gateway's `rulesEngineEnabled` is false.
Configure and verify Trino OAUTH2 over HTTPS on both coordinators first; only
then set the selector flag to `true` and enable the external rules engine.

The Gateway's external rules engine posts Trino request metadata to
`http://routing-api.default.svc.cluster.local:8080/gateway-rules`. The
`Authorization` header is intentionally forwarded to the selector for JWT
validation; do not add it to `excludeHeaders`. The original request is still
proxied to the selected coordinator, where Trino must authenticate the user
independently. The callback returns routing group `georestricted` for `US`
access to `trades_raw`, denies that catalog for `UK`, and returns `adhoc` for
`tpch`.

## Security and POC limits

The checked-in install command pins Gateway chart version `1.21.0`. Gateway
routes follow-up Trino protocol requests by query ID; OAuth challenge/callback
affinity must still be exercised on the deployed chart. The selector's
returned policy errors are propagated, but Gateway can fall back to a
client-supplied routing-group header when the selector is unreachable. Strip
`X-Trino-Routing-Group` at a trusted ingress, keep coordinators private, and
enforce authorization in Trino. Direct coordinator access bypasses Gateway.

The present Trino values are HTTP-only and do not configure OAUTH2, TLS, or
Trino access control. Do not treat the selector change alone as satisfying
end-user authentication or data-residency enforcement. See the repository-root
[POC limitations](../../POC_LIMITATIONS.md) and [selector guide](../../trinoGateway/README.md).
